5. CONTRATO HTTP COMÚN

Prefijo: /api/v1. JSON con campos camelCase; tablas/columnas SQL snake_case. Identificadores: enteros positivos. Instantes: RFC 3339 con zona u offset; el backend responde en UTC con Z. Fechas civiles: YYYY-MM-DD. Zona de negocio: America/Argentina/Buenos_Aires; no interpretar fechas civiles como UTC en el navegador.

Respuesta de un recurso: {"data": {...}}. Listado: {"data": [...], "meta": {"page": 1, "pageSize": 20, "total": 0}}. page >= 1; pageSize entre 1 y 100, por defecto 20. Orden estable por id ascendente salvo clases (startsAt, id), paquetes (expiresOn, assignedAt, id) e historial (startsAt descendente, id descendente).

Los filtros no otorgan permisos: memberId o professorId enviados por un cliente nunca sustituyen la identidad autenticada. Los listados restringidos aplican el alcance en la consulta, antes de contar o paginar. Recurso ajeno: 403 sin datos privados; inexistente: 404.

Error: {"error": {"code": "CLASS_FULL", "message": "No hay cupos disponibles.", "fields": {}}}. fields relaciona nombres de campos con mensajes cuando corresponde; nunca contiene trazas SQL, hashes ni tokens.

Códigos HTTP: 200 consulta/actualización/acción exitosa; 201 creación; 204 cambio de contraseña sin cuerpo; 400 JSON o filtros inválidos; 401 credenciales/sesión inválida; 403 permisos; 404 inexistente; 409 duplicado o conflicto de estado/negocio; 422 campos inválidos; 500 error inesperado sin detalles internos.

Códigos estables de negocio: EMAIL_IN_USE, NAME_IN_USE, INACTIVE_USER, INVALID_PROFESSOR, INACTIVE_ACTIVITY, CLASS_FULL, CLASS_CANCELLED, CLASS_STARTED, ALREADY_ENROLLED, NO_USABLE_PACKAGE, CANCELLATION_WINDOW_CLOSED, ALREADY_CANCELLED, CAPACITY_BELOW_ENROLLMENTS, CLASS_HAS_ENROLLMENTS, INVALID_ATTENDANCE, PACKAGE_ASSIGNMENT_EXISTS. Para 401 de login usar INVALID_CREDENTIALS sin revelar si el correo existe o la cuenta está inactiva.

No hay DELETE físico de usuarios, clases, actividades, tipos o inscripciones. Se conservan estados e historial. Tampoco hay endpoints de pagos, listas de espera, notificaciones o recuperación automática de contraseña.

6. SESIÓN, CONTRASEÑAS Y PERMISOS

Roles técnicos: ADMIN, PROFESSOR y MEMBER. Las etiquetas visibles son Administrador, Profesor y Socio. Un usuario inactivo no puede iniciar sesión ni operar aunque conserve un JWT emitido anteriormente: el middleware consulta el usuario actual y su rol en cada petición privada.

Authorization: Bearer <token>. JWT firmado con HS256, algoritmo permitido explícitamente; sub es el id del usuario como texto; iat y exp, duración de 3600 segundos; iss=gymflow; aud=gymflow-web. Se verifica firma, algoritmo, vencimiento, emisor y audiencia. El rol del JWT no reemplaza al rol actual de la base.

El contexto que recibe un módulo del backend es req.user = {id, role}; nunca un id que provenga del cuerpo. La base entrega requireAuth y allowRoles(...roles). La propiedad del recurso sigue siendo responsabilidad del módulo: por ejemplo, Emilia verifica que la clase pertenezca al profesor.

Contraseñas nuevas: de 12 a 128 caracteres, sin truncarlas ni aplicar trim. Hash Argon2id con sal individual; parámetros mínimos de coordinación: memoryCost 19456 KiB, timeCost 2, parallelism 1. Nunca devolver passwordHash. La biblioteca concreta y su versión se fijan en el manifiesto inicial. Validar credenciales con la función de verificación de la biblioteca, no comparando hashes manualmente.

Token solo en memoria del proveedor de sesión React, no en localStorage ni en la URL. Recargar la pestaña vuelve a pedir login: es una simplificación explícita del MVP. Al cerrar sesión se borra el token y los datos privados del frontend. No se implementan refresh tokens ni revocación centralizada, que los módulos excluyen. Un token copiado sigue válido hasta expirar mientras la cuenta permanezca activa; no afirmar que logout lo revoca en el servidor.

Cambiar contraseña requiere la actual y la nueva; invalida la sesión del navegador mediante limpieza local y nuevo login. No promete revocar otros JWT emitidos. Producción usa HTTPS y CORS limitado al origen del frontend. No agregar un bypass de autenticación para integrar la parte de Emilia.

Matriz resumida:
- ADMIN: gestiona socios/profesores, actividades, clases, tipos, paquetes e inscripciones; registra asistencia e inspecciona historiales y panel.
- PROFESSOR: consulta solo sus clases, su lista de inscriptos y sus asistencias; puede registrarlas/corregirlas. No consulta paquetes de otros ni listados generales de socios.
- MEMBER: consulta actividades activas y programación pública para usuarios autenticados; ve y gestiona únicamente sus inscripciones, paquetes e historial.
- Todos: consultar su identidad, editar nombre/correo propios y cambiar su contraseña, según UI-03 y UI-04. No pueden cambiarse rol ni estado.

La vista de calendario general para profesores contradice RN-04 y la matriz de módulos. Para esta base se conserva el permiso más restrictivo: solo clases asignadas. El contrato no habilita calendario ajeno ni acceso a inscriptos de otras clases. Es una resolución explícita para trabajar, no una aprobación atribuida al tutor; si confirma el calendario general, cambiar solo el alcance de lectura básica sin abrir asistencia ni datos personales de clases ajenas.

7. MODELO DE DATOS OBJETIVO

Se mantienen las seis entidades del DER. Asistencia vive en la inscripción, no en una segunda tabla con el mismo estado. El nombre SQL class_reservations se conserva; el modelo de dominio y HTTP se llama Enrollment. Prisma podrá usar @@map("class_reservations") y @map para columnas sin duplicar entidades.

users: id; name (120); email normalizado (255, único); password_hash; role; active. No cambios de rol en PATCH ni borrado físico. Las cuentas ADMIN iniciales son del seed; no se agrega una pantalla de creación de administradores.

activities: id; name (100); description nullable (1000); active. Nombre sin duplicados por mayúsculas o espacios laterales.

classes: id; activity_id; professor_id; starts_at y ends_at TIMESTAMPTZ; capacity entero > 0; cancelled. Ocupados = inscripciones no canceladas; disponibles = capacity - ocupados. No guardar un segundo saldo de cupos.

package_types: id; name (100, único sin distinguir mayúsculas); class_credits y duration_days enteros > 0; active. Desactivar un tipo impide nuevas asignaciones, pero no invalida los paquetes ya entregados.

member_packages: id; member_id; package_type_id; starts_on y expires_on DATE; initial_credits; remaining_credits; assigned_at TIMESTAMPTZ. Guardar créditos iniciales como snapshot: modificar el tipo no cambia saldos ni vigencia de asignaciones existentes. La fecha de vencimiento también es un snapshot. El nombre mostrado proviene del tipo vigente.

class_reservations: id; class_id; member_id; member_package_id; cancelled; created_at; cancelled_at nullable; credit_refunded; attendance_status (PENDING, PRESENT, ABSENT); attendance_recorded_by y attendance_recorded_at nullable. El id del socio se guarda para garantizar unicidad por persona y clase; una FK compuesta comprueba que el paquete pertenece a ese socio.

Cada inscripción nace con asistencia PENDING y sin autor/fecha de registro. Registrar PRESENT o ABSENT fija ambos. Corregir reemplaza el estado y la última persona/fecha que lo registró; no se promete un historial completo de cada edición. No se almacenan motivo ni autor de cancelación, tal como dice el diseño. cancelled_at y credit_refunded permiten controlar estado y devolución, no agregan un motivo.

Restricciones en SQL: saldo entre cero y créditos iniciales; capacidad positiva; fin posterior a inicio; duración/créditos positivos; claves foráneas sin cascadas de borrado; índice único parcial de (class_id, member_id) cuando cancelled=false. Así se impide duplicar una reserva usando dos paquetes distintos y se permite reinscribirse después de cancelar conservando las filas antiguas.

Unicidad de asignación: mismo socio + tipo + fecha de inicio no se asigna dos veces; devuelve 409. Sí puede tener varios tipos o asignaciones de fechas distintas, con vigencias superpuestas.

Los CHECK e índices parciales del SQL son parte del modelo, aunque Prisma no los exprese directamente. Incorporarlos como SQL en la migración inicial; no confiar solo en el esquema generado. modelo_objetivo.sql es referencia para una base nueva y no sustituye una migración desde el script publicado.

8. FECHAS, PAQUETES Y ESTADOS DERIVADOS

La vigencia incluye startsOn y expiresOn. Al asignar un tipo de D días: expiresOn = startsOn + D - 1 días calendario, en la zona de negocio. Un paquete de un día vence ese mismo día. Esto precisa la semántica que los documentos no cerraban; el CHECK viejo ya permitía igualdad de fechas.

Un paquete utilizable tiene saldo positivo y cubre tanto la fecha actual de negocio como la fecha de inicio de la clase. El socio debe estar activo. Se elige por expiresOn ascendente, assignedAt ascendente y, como desempate estable, id ascendente. No se obliga al socio a seleccionar ni enviar el paquete manualmente.

Estado de paquete, sin almacenarlo aparte: NOT_STARTED si hoy es anterior a startsOn; EXPIRED si hoy es posterior a expiresOn; EXHAUSTED si está vigente y sin saldo; ACTIVE si está vigente y con saldo positivo. Próximo a vencer = ACTIVE y faltan entre 0 y 7 días calendario inclusive. No incluye vencidos ni sin saldo.

Estado de clase derivado: CANCELLED si cancelled; FINISHED desde endsAt inclusive; IN_PROGRESS desde startsAt inclusive y antes de endsAt; SCHEDULED antes de startsAt. Las inscripciones solo se crean para SCHEDULED. Todas estas comparaciones se resuelven en el servidor.

Para no alterar reservas existentes silenciosamente, una clase con inscripciones activas permite cambiar solo capacity, siempre que no quede por debajo de la ocupación. Cambiar actividad, profesor u horario en ese caso devuelve CLASS_HAS_ENROLLMENTS; la alternativa es cancelar y programar otra clase. Es una política técnica de coordinación propuesta aquí para cerrar un caso no especificado, no una regla confirmada del tablero. Debe revisarse con los criterios de HU-15 antes de adoptar una política distinta.

La programación y edición operan sobre clases futuras. La asistencia se registra desde el inicio; no se marca un socio ausente solo porque todavía no se tomó asistencia. Los estados históricos permanecen consultables.

Desactivar socio/profesor/actividad no borra ni cancela automáticamente clases, reservas o paquetes. Impide operar a la cuenta y usar esa entidad en nuevas operaciones. Los compromisos ya programados requieren gestión explícita del administrador. Así no aparece una cancelación cruzada oculta dentro del módulo de usuarios.

9. INSCRIPCIÓN Y CONCURRENCIA

POST /enrollments recibe classId. MEMBER se inscribe a sí mismo; ADMIN además envía memberId del socio al que asiste. Un MEMBER no puede utilizar memberId para actuar por otra persona. La identidad del profesor nunca habilita una inscripción.

Antes de confirmar, GET /classes/{id}/eligibility devuelve si puede inscribirse, el motivo de rechazo o el paquete seleccionado y su saldo posterior esperado. Es una consulta para la confirmación prevista en el diseño; no reserva lugar ni congela un saldo. El POST vuelve a validar todo.

La operación real es una transacción:
1. Bloquear la fila de la clase y volver a comprobar estado, horario y cupo.
2. Bloquear la fila del socio; comprobar estado/rol. Esto serializa también sus reservas simultáneas en clases diferentes.
3. Buscar paquetes utilizables, bloquearlos por id ascendente y seleccionar entre ellos por expiresOn, assignedAt e id.
4. Verificar que no exista inscripción activa del mismo socio/clase.
5. Insertar la reserva, descontar exactamente un crédito y confirmar juntos.

Usar SELECT ... FOR UPDATE parametrizado dentro de la transacción de Prisma, o un mecanismo equivalente que pruebe las mismas garantías. No interpolar valores del usuario en SQL. Todos los flujos que modifican cupos/saldos respetan el mismo orden de bloqueo: clase, socios por id, paquetes por id, reservas por id. Si una transacción falla, no queda un descuento parcial.

La restricción única parcial es una protección adicional, no reemplaza el control concurrente de cupo y saldo. Capturar conflictos y responder con el código de negocio correspondiente, no con un 500 que revele SQL.

10. CANCELACIONES Y ASISTENCIA

Cancelación individual: permitida hasta startsAt menos dos horas, inclusive. Exactamente dos horas antes sí se acepta; un instante después ya no. La petición tardía se rechaza con 409 CANCELLATION_WINDOW_CLOSED, sin liberar cupo ni devolver crédito. Esta regla se toma de Trello confirmado y del diseño, por encima del texto viejo de MOD-06 que permitía cancelar tarde.

Una cancelación válida marca cancelled, fija cancelledAt, suma un crédito al mismo paquete y marca creditRefunded, todo dentro de una transacción. Si el paquete ya venció, recupera el saldo contable pero no se extiende su fecha. Repetir cancelación devuelve 409 ALREADY_CANCELLED y no vuelve a acreditar. Administración no elude el límite individual por un parámetro oculto.

Cancelar una clase es distinto: ADMIN cancela la clase y todas sus reservas activas, devolviendo cada crédito al paquete de origen sin aplicar el límite de dos horas. No se reembolsa por segunda vez una inscripción ya cancelada. La operación es atómica y la repetición se rechaza con 409, como exige HU-16. Si existía asistencia, se conserva el dato histórico pero el historial muestra la clase cancelada y no la computa en el porcentaje de asistencia.

PRESENT/ABSENT se registra solo en inscripciones confirmadas y clases no canceladas, desde startsAt. ADMIN puede hacerlo en cualquiera; PROFESSOR solo en la asignada. MEMBER nunca registra asistencia. La ausencia no genera devolución.

PUT /classes/{id}/attendance recibe una lista sin ids repetidos. Valida permisos y pertenencia de todas las inscripciones antes de guardar; si una falla, rechaza el lote entero. Marcar todos presentes se construye en el frontend y envía esa misma operación, no agrega una regla o API diferente. El botón Restablecer solo limpia cambios sin guardar; no borra registros del servidor.

Porcentaje de asistencia = PRESENT / (PRESENT + ABSENT) * 100, redondeado a una decimal. Excluir PENDING y cancelaciones; si el denominador es cero, devolver null y mostrar 'Sin registros', no 0% ficticio.
